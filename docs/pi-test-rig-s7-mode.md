# 3-Pi test rig, S7 mode — no wiring required

This is a second way to run the 3-Pi test rig (see `docs/pi-test-rig.md`
for the original, physically-wired version), aimed at getting a first
end-to-end result fast: **no GPIO wiring, no resistors, no multimeter.**
Pi #1 and Pi #2 just need to be on the same network.

Starting from scratch (blank SD cards)? See `docs/pi-hardware-setup.md`
first — flashing, first boot, and SSH access, before any of this.

| Pi | Role | What runs on it |
|---|---|---|
| **Pi #1** | Virtual machine — now an S7 PLC simulator | `plc-simulator/plc_simulator.py` — a real Siemens S7 protocol server (S7comm, TCP port 102) standing in for a real PLC |
| **Pi #2** | Edge computer | `s7_bridge.py` + `@mes/edge-agent` — polls Pi #1's PLC over the network, publishes MQTT events, buffers/retries |
| **Pi #3** | Backend computer | unchanged — same as the GPIO version |

`@mes/edge-agent`, the backend, and the dashboard are exactly the same
code either way — only which `SignalSource` the edge agent uses changes
(`SIGNAL_SOURCE=s7` instead of `gpio`). Nothing about MQTT, buffering,
retries, the database, or the dashboard cares which one is running.

This isn't just a shortcut for testing, either. A real S7-300/400/1200/
1500 PLC talks this exact same protocol (S7comm) — this mode is a genuine
first test of a real machine-connectivity path (the kind PRD Section 5.5
and ROADMAP M1 describe), not a placebo you'll throw away once the GPIO
rig works. If Emlid's own line, or a future customer's, has a Siemens PLC
on it, this is close to the real adapter already.

**Verified in the sandbox this was built in** — the S7 server, the S7
client/bridge, the edge agent, the backend, and Postgres were all run
together over real TCP sockets (loopback, standing in for your LAN) end to
end: parts and status changes generated by the simulator showed up
correctly in the database and via `/api/machines`, with zero events lost.
That's not a claim about your specific Pi hardware or Wi-Fi — only you can
verify that — but the protocol logic, the polling/diffing math, and the
whole pipeline downstream of it are confirmed working, not just written.

## Why polling instead of pulses

The GPIO version reacts to edges — a pin goes high, that's a part. A PLC
doesn't work that way: it just holds a counter that goes up over time,
and you read it whenever you ask. So `s7_bridge.py` polls Pi #1's PLC
memory on a fixed interval (`POLL_INTERVAL_MS`, default 300ms) and
compares this read to the previous one — any increase in the good/scrap
counters becomes that many `production_count` events, and any change in
the running/down bit becomes a `machine_status` event. This is also
exactly the shape a real OPC-UA or Modbus adapter will take later (PRD
5.5) — this mode is a dry run of that pattern, using S7 as the first real
protocol instead of a placeholder.

## Data layout

Pi #1's simulated PLC exposes one data block (DB1, 16 bytes) that Pi #2
reads from. This layout is arbitrary (a real PLC's program would define
its own), but `plc_simulator.py` and `s7_bridge.py` have to agree on it —
they do, today:

| Offset | Type | Meaning |
|---|---|---|
| byte 0, bit 0 | BOOL | Running (1) / down (0) |
| bytes 4-7 | DINT (32-bit) | GoodCount — cumulative good parts |
| bytes 8-11 | DINT (32-bit) | ScrapCount — cumulative scrap parts |

## 1. Install python-snap7 on Pi #1 and Pi #2

Good news: `python-snap7` version 3.x is **pure Python** — no `libsnap7`
C library, no apt package, no build step. The install is the same one
line on any machine, Raspberry Pi included:

```bash
pip install python-snap7 --break-system-packages
```

(`--break-system-packages` is needed on recent Raspberry Pi OS and on
Debian 12+ generally, both of which block plain `pip install` outside a
virtual environment by default — this flag is the same escape hatch used
elsewhere for `pip`-installed tools on this project. A venv works too, if
you'd rather use one. Unlike the GPIO mode, there's nothing else
OS-specific here — `python-snap7` is pure Python either way.)

If you haven't already, get the code onto both Pis per Section 0 of
`docs/pi-test-rig.md` (unzip on your Mac, `scp -r` to each Pi's `~/mes`).
That process is identical here — this mode just uses a different
subfolder (`plc-simulator/`) and a different env var (`SIGNAL_SOURCE=s7`).

## 2. Pi #1 — S7 PLC simulator

```bash
cd ~/mes/plc-simulator
python3 plc_simulator.py
```

You should see:

```
S7 PLC simulator listening on :102, DB1 (16 bytes)
```

It's now generating simulated parts/scrap/status changes and serving them
over the network on port 102 — the same port a real Siemens PLC uses.

Tunable behavior via env vars (defaults shown, same idea as
`virtual_machine.py`'s):

```bash
AVG_CYCLE_SECONDS=3.0     # average time between parts
SCRAP_RATE=0.08           # fraction of parts that come out scrap
AVG_UPTIME_SECONDS=60.0   # average running stretch before a down event
DOWNTIME_SECONDS=10.0     # how long a down stretch lasts
TCP_PORT=102              # change only if 102 is already in use on this Pi
```

Port 102 is a low/"privileged" port on Linux — if you get a permission
error binding it, either run with `sudo`, or set `TCP_PORT=1102` (and
point Pi #2's `PLC_PORT` at the same value) to avoid needing root.

To have it start automatically on boot instead of running it by hand, see
`plc-simulator/README.md` for the matching systemd unit
(`plc-simulator.service`), same pattern as `virtual-machine.service` in
the GPIO mode.

## 3. Pi #2 — edge computer, S7 mode

Install Node/pnpm if you haven't already (see `docs/pi-test-rig.md`
Section 3), then:

```bash
cd ~/mes
pnpm install
pnpm --filter @mes/shared build
pnpm --filter @mes/edge-agent build
```

Run the edge agent pointed at Pi #1's PLC and Pi #3's broker:

```bash
SIGNAL_SOURCE=s7 \
MACHINE_ID=s7-rig-01 \
MQTT_URL=mqtt://<pi3-ip>:1883 \
PLC_IP=<pi1-ip> \
pnpm --filter @mes/edge-agent start
```

Full list of S7-specific env vars (defaults shown):

```bash
PLC_IP=127.0.0.1        # Pi #1's IP — REQUIRED, has no useful default across two Pis
PLC_PORT=102            # must match Pi #1's TCP_PORT
PLC_RACK=0              # rack/slot are S7 addressing concepts with no
PLC_SLOT=1              # real meaning for the simulator — leave at defaults
POLL_INTERVAL_MS=300    # how often to read Pi #1's PLC memory
```

You should see:

```
edge agent started {"machineId":"s7-rig-01","topic":"machines/s7-rig-01/events","source":"s7"}
connected to broker {"url":"mqtt://<pi3-ip>:1883"}
[s7-bridge] connected to PLC at <pi1-ip>:102
machine status changed {"status":"running", ...}
```

followed by `part event` log lines as Pi #1's simulated counters climb.

## 4. Pi #3 and the dashboard

No changes from `docs/pi-test-rig.md` Sections 4-5 — same backend, same
Postgres, same Mosquitto config, same dashboard command. This mode only
changes what Pi #1 and Pi #2 are doing.

## 5. Verify in stages

Same instinct as the GPIO guide — check each hop before trusting the
whole chain:

**Pi #1 alone** — run `plc_simulator.py` and confirm the "listening on
:102" line appears; that's the whole PLC simulator, no client needed yet.

**Pi #1 → Pi #2, without the edge agent** — from Pi #2, run the bridge
script directly:

```bash
cd ~/mes/packages/edge-agent/python
PLC_IP=<pi1-ip> python3 s7_bridge.py
```

You should see `connected to PLC at <pi1-ip>:102` on stderr and JSON lines
on stdout as Pi #1's counters change — no MQTT, no backend involved yet.
If this hangs instead of connecting, it's a network/firewall problem
between the two Pis, not an application bug — check both Pis are on the
same subnet and that nothing blocks TCP port 102 between them.

**Full stack** — once that's confirmed, bring up the edge agent (step 3),
backend (step 4), and dashboard as normal.

## 6. Troubleshooting

**Pi #2 hangs on "connected to PLC" and never shows events** — this
usually means `PLC_IP` is wrong (double check with `hostname -I` on
Pi #1) or Pi #1's simulator isn't actually running. `s7_bridge.py`
reconnects on its own every few seconds if the connection drops, so a
transient network blip during setup isn't fatal — give it a few seconds
after fixing the address.

**"Address already in use" on Pi #1** — something else is already
listening on port 102 (or 1102, if you changed it) — check with
`sudo netstat -tlnp | grep 102` and either stop that process or pick a
different `TCP_PORT`/`PLC_PORT` pair.

**Counts in the dashboard don't match what you'd expect from the cycle
settings** — remember `s7_bridge.py` polls every `POLL_INTERVAL_MS`; if
multiple parts complete between two polls, they show up as separate
events on the *next* poll, all at once, not spread out in real time. This
is expected and mirrors how a real PLC integration would behave too —
lower `POLL_INTERVAL_MS` for finer-grained timing if it matters for a demo.

## 7. Then try the physical rig

Once this mode is working end to end, `docs/pi-test-rig.md` walks through
swapping Pi #1 for a real discrete-I/O simulator with actual GPIO wiring —
useful because not every real machine exposes an S7 (or OPC-UA/Modbus)
interface; some only have raw digital signals. Both modes plug into the
exact same `SignalSource` interface, so nothing else about the system
changes between them.
